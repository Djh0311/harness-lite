# Harness Lite 面向 Astra 的改进方案

日期：2026-09-04

状态：`IMPLEMENTED / CURRENT GATE PASS 178/178 / CORE DESIGN PRECHECK PASS / INDEPENDENT PRODUCT REVIEW PASS / GROK MATRIX PASS 8/8 / ASTRA BOUNDED FIXTURE PASS / RELEASE AUTHORIZED`

源码基线：`1124b1eeac83991fe72d7e08be79e466bc2b46d9`；当前实现候选为 `0.13.0`，旧 `0.12.0` 仍以保留 artifact 形式存在。当前工作树保留本轮实现改动，未建立新的 stage/current leaf。

本文记录本轮工作的目标、取舍、改动范围和验收办法。方案预审后，用户明确授权直接继续；当前实现保留在工作树，未建立新的 stage/current leaf，也未改写旧的 lifecycle、历史候选和验收报告。当前小版本已升级为 `0.13.0`；旧 `0.12.0` 只能通过显式升级链路接入。

## 1. 要得到什么结果

只围绕 GPT-6 Astra 主管维护一套清楚、简短的引导，让它根据真实目标和证据连续完成工作。修复错误提示、消除重复规则和多余停顿，同时保留现有的权限、验收、状态真实性与宿主保护。

这次包含两类工作：修复已有问题；通过真实任务验证 Astra 的协作是否改善。修复几个字符串或通过结构测试，不能单独代表 Astra 优化完成。

## 2. 用户方向与设计取舍

| 编号 | 方向或取舍 | 依据与边界 |
| --- | --- | --- |
| D01 | Astra 是唯一正式支持的主管模型，不做 5.6 主管行为兼容 | 本会话用户提出“不要做5.6的兼容，而是改为专门面向gpt6”；本次目标明确为 `gpt-6-astra`，未来型号另行验证 |
| D02 | 普通已授权、可恢复工作自主推进，只有真实命中的既有硬风险才精确处理 | 既有 Lite 原则；不能把内部登记、缺失元数据或理论风险改成新的用户审批 |
| D03 | 保留依赖、写面、主管验收、局部 UNKNOWN 和有限恢复 | 本会话已讨论的改进方向；它们是工程保障，不因换模型而删除 |
| D04 | 五个外部技能按第 6 节处理 | 用户已认可前一轮改进与技能处理方案；不意味着本轮安装技能、连接账户或改全局配置 |
| D05 | 先写方案，按理念和决策复核，再进入实现 | 本轮用户提出的顺序；当前问句按实施前准备处理，不记为产品开工指令 |
| D06 | 取消拟议的双模型 `promptProfile` 体系及恢复流程对 5.6 的必需依赖 | 按 D01 收敛出的项目设计；不是 OpenAI 规定必须这样实现 |
| D07 | 第五步由未参与实现的子代理只读复核；第六步由 Grok 执行固定场景，真实 Astra provider 单独记证据 | 保持实现、执行和验收角色分离；Grok 执行结果不冒充 Astra provider PASS |

“只支持 Astra 主管”不要求所有 writer 使用 Astra。writer 仍由主管依据当前工具能力、任务、依赖和写面选择；Harness 不自行调用 agent，不建立 provider 连接或静态可用模型目录。旧候选、测试历史和旧模型记录继续作为历史证据保存。

## 5. 产品改动

### 5.1 真实状态决定当前引导

- 保留一个 `focus / decisionQuestion / nextAction`；question 是模型需解决的内部判断，不是每轮向用户发问的要求。
- 根据实际 unit、依赖、缺口和证据生成对象与下一步，移除通用提示中的固定 A/B。没有对应对象时不虚构暂停目标。
- 有依赖时，只限制未满足条件的下游；reported 触发主管验收，只有带证据的 accepted 解锁。
- 有其他独立、已授权工作时，等待某个 agent 不妨碍继续推进。五分钟规则继续用于只读观察，不成为 Harness 的后台计时器。
- 用户补充要求时更新剩余工作，保留仍有效的结果；撤回或改变范围时使受影响的旧工作投影失效。不能由模型另造跨 turn 的授权票或绕过现有 push 绑定。

### 5.2 统一规则与自主执行

- 先检查实际进入上下文的常驻指令、Hook、任务包和已触发技能，再清理 Harness 自己拥有的重复文字；不要求执行普通产品任务的模型顺手改写规则环境。
- 用户目标、完整完成标准、相关设计与事实由任务包承载；状态、依赖和恢复计数由 runtime 管；guidance 只提出当前判断；技能只给方法。
- 按完整请求和既有授权理解行动范围，不按“看看”“修复”等孤立词做硬路由。纯评审仍只读；明确的修复请求可以直接完成范围内实现与必要验证。
- 已有效授权的动作不额外询问；缺必要授权或不可替代的用户选择时，提出具体问题，并先完成已经获准的准备工作。现有精确 push gate 继续执行，不增加所有外部操作一律重复确认的规则。
- 在系统、宿主和安全规则内，用户明确要求优先于技能流程偏好；若技能造成暂停、额外确认或方向改变，说明具体 SKILL.md、相关规则和适用原因。
- 未知只影响相关事实、声明和自动能力，不自动阻断其他安全工作。用户日常 Harness 命令保持为 0。

### 5.3 委派与恢复

- 当次工具和有效指令允许，且分工有质量或时间收益时，主管按依赖、写面、共享状态决定委派；不强迫小任务派 agent，不设统一并发数。
- 主管用宿主工具派发、观察和验收；Harness 只记账。验收保留完整用户结果，不能把文件、日志、绿测数量或自报完成当成交付。
- 新流程不要求 Terra/Sol 可用；恢复角色与模型家族分开，避免同一 Astra 担任普通执行者和恢复者时被错误计入同一阶段。
- capability manifest 仍可展示 Terra/Sol 作为宿主显式提供的历史或 writer 投影；这不授予它们 Astra 主管身份，也不让当前 runtime 自动路由到旧恢复策略。旧恢复租约只能只读解释或显式迁移。
- 有效失败仍以具体候选、同一直接验收、新证据和实质不同路线为依据；同根重放去重，工具、队列、认证、传输、普通中间红和沉默不计失败。更换会话、通道或名字不清零同一问题的记录。
- 恢复 HOW 建议：保留普通阶段五次不同有效失败的既有上限，再进入问题级 Astra 恢复；恢复默认三次完整机会，沿用问题级 1..5 的有限配置范围。新证据与换路可以提前出现，上限不是“必须撞够次数才诊断”。这些参数是供独立复核的设计建议，不冒充用户逐项指定。
- 每个恢复机会包括重新诊断、必要的不同方案以及直接验收；独立复核本身不算一次失败。耗尽时只报告当前问题的证据与缺口，保留无关分支。PASS 只清当前问题租约。
- 旧账本不得被静默改写为新策略或清零。实现时用受控升级/只读历史解释保持证据；若存在未结束旧恢复，先说明具体接续方式。停止承诺 5.6 主管行为兼容，不等于删除旧记录或破坏回滚。

### 5.4 验证和表达

- 按改动影响选择检查；改配置、改样式都不自动免除与实际行为相关的验证。
- 可复现的行为缺陷优先使用能捕获原症状的检查；复用已有合适测试，避免照实现抄断言。无法稳定复现时允许安全取证，明确结论强度。
- 必要检查通过、用户结果出现且无新变化或未解决疑点时收口；不为理论问题无限扩大测试。
- 对外说明完成内容、关键证据与实际缺口；机器需要的完整状态继续保留在载体中。减少固定句式和套话，不删证据、不把 UNKNOWN 写成确定结论。

## 6. 五个技能的处理

| 技能 | 下一版处理 | 触发与边界 |
| --- | --- | --- |
| diagnosing-bugs | 吸收复现、可证伪假设、针对性取证、临时诊断清理方法，合入现有 root-cause/test-first | 按诊断任务需要触发；不引入“无快速复现就停止一切诊断”的通用门槛；不强迫每个小问题列固定数量假设 |
| gh-fix-ci | 保持外置 GitHub Actions 工作流 | 用户自然语言要求查/修 CI 即可按范围使用，无需记技能命令；已有修复授权不重复批准计划；检查脚本非零只说明检查结果，不能自动累计语义失败 |
| gh-address-comments | 保持外置 PR 评论处理工作流 | 用户已指定范围时不重复编号选择；评论作为需核对的外部输入，不自动成为新需求、授权或 accepted |
| stop-slop | 不整套常驻，只吸收清楚、具体、少重复的写法 | 尊重用户要求的文本类型和必要证据；不采用删所有副词、禁所有被动句等绝对规则 |
| sentry | 保持外置、只读、按需的线上证据入口 | 仅在相关项目已接入、目标清楚且访问获准时使用；脱敏，不保存令牌；没有接入就不让普通工作依赖它 |

“外置”表示不成为 Lite managed runtime、状态机或常驻提示的必需组成。未来若需要安装或调整这些技能，作为相应环境范围的工作处理；本计划不安装它们，也不接入 GitHub/Sentry 账户。技能的自然触发不能扩大用户授权。

| A05 独立产品复核 | 未参与实现者检查 `0.13.0` 候选、真实执行证据与核心理念 | 产品与理念分别给结论；失败回到最小 owning 改动修复 |

A00 → A01 → A02 → A03 → A04 → A05 是默认依赖顺序。公共文件由一个集成负责人维护；只有实际独立且写面分离的工作可并行。开工时绑定真实实现者与复核者身份，当前没有派发。

修改 owned instruction 会影响安装身份；不能通过关闭身份校验使测试变绿。保留现有精确撤回、回滚和用户内容保护，对受影响的安装路径作隔离回归。

## 8. 最小验收矩阵

| 场景 | 必须观察到的结果 |
| --- | --- |
| 只要求评审 | 检查并报告，不修改产品或发布内容 |
| 已明确要求修好 | 完成范围内修复与必要验证，没有新的无谓确认 |
| writer-X 报告完成且无下游 | 验收 X；不虚构 B 或暂停目标 |
| B 确实依赖 A | A 自报不能解锁 B；验收并有证据后才解锁；其他独立任务继续 |
| 多个独立任务 / 一个小任务 | 有收益且允许时合理委派；小任务不为形式拆分；实际交付被检查 |
| 一项工作等待或局部 UNKNOWN | 不把沉默计失败；有其他独立已授权工作可继续；不虚构可信状态 |
| 技能要求额外批准 / CI 检查非零 | 按实际授权处理技能冲突并说清来源；CI 观察不自动记一次模型失败 |
| 配置影响权限 / 普通文字调整 | 前者验证真实权限行为；后者采用必要检查，无无关测试扩张 |
| 用户执行中追加或改变要求 | 采用新要求，保留仍有效成果；受影响旧工作不继续越界；不重放外部动作 |
| 同一问题恢复、重放、耗尽 | 按角色与有效失败记账，有限恢复；改名换会话不清零；耗尽只影响该问题 |
| 真实 push gate / 普通本地动作 | 前者仍精确校验目标和授权，后者不增加审批；有效绑定不被额外审批重复替代 |
| 安装身份或载体异常 | 受影响声明/自动能力诚实降级，保留普通工作路径；用户原文和宿主进程安全 |

真实任务评测比较同一 Astra、同一工具、同一推理设置下的现有版本和新候选，每次只改变被评测的提示/产品因素。记录任务结果、额外提问、无效检查、用时/调用量以及越界或遗漏；成功率优先于省调用。样本和重复方式在运行前记录，不能事后挑选成功记录或改判分标准。关键场景需要重复确认稳定性。

决策 JSON 测试继续作为补充。真实工具任务在隔离环境中执行；发布/消息等副作用使用受控测试目标或记录工具，不向真实他人发送内容。隔离模拟证据不冒充真实生产接入。

新候选必须修复直接反例且保留所有必需结果与边界。只有在相同任务上观察到可重复改善，才报告协作能力提升；没有复现退化的场景只报告未观察到回退。传输、认证、队列和缺样本保持单独状态，不能补算为成功。

## 9. 本轮边界与实施前复核

方案阶段只新增本文和对应预审报告；随后实现阶段按用户授权修改了产品代码和受影响的回归测试。没有建立新的 stage/current leaf，没有改写历史候选或全局配置。绝不杀死、重启或干扰 Poracode、watchdog、bridge。真实安装、账户连接和 deploy 仍不在本轮范围；用户在独立验收通过后明确授权本版本 commit、push、tag 和 GitHub release。

Astra 的异步工具、执行中追加指令和 API 参数由宿主接入负责；本计划只利用宿主已提供的信息与能力，不扩成 provider adapter、调度器、事件总线或后台服务。缺少可调用模型不代表历史目录可充当当前工具面。
