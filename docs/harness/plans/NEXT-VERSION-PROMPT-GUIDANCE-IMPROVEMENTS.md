# Harness Lite 下一版本：从规则提示转向决策引导

状态：`DESIGN INPUT / NEXT UPGRADE / NOT ACTIVE / NOT DISPATCHED`

来源：2026-09-01 用户在 Harness Lite 0.11 完成后补充的核心判断。本文把本轮讨论沉淀为下一次升级必须处理的产品改进点；它不是 current authority、stage、leaf、Kickoff、实现授权、candidate 或 release。

当前产品基线：Harness Lite `0.11.0`，retained candidate 为 `docs/harness/artifacts/harness-lite-0.11.0-8e14e641b7d0fe3641a5e74c49b11a60761e0dc63fb75866ff8226e6b3687ae5.json`。本文位于 `docs/harness/plans/**`，不属于当前 candidate builder 输入，不得改变已接受的 0.11 candidate 身份。

## 一、这次新增的核心判断

模型对提示词和当前上下文仍然高度敏感。一个语义进入上下文后会占据注意力；同一语义在全局规则、常驻内核、Hook、leaf、skills 和任务包中反复出现，会进一步放大它的显著性。

这不是简单的“字符太多”，也不能机械理解为每重复一次就增加固定权重。真正的产品问题是：

- 模型会优先围绕上下文中反复出现的概念组织判断和行动；
- 即使文字写的是“不要回滚、不要停止、不要扩大边界”，被持续激活的仍然是回滚、停止和边界；
- 模型可能在语义上逐条遵守 Harness，却在实践中把主要精力放在治理正确、安全自证和形式闭环，而不是用户真正需要的结果；
- 具体禁令和失败例子越多，越容易让模型在无关场景寻找同类风险、错误类推或采用保守默认路线。

因此下一版本的目标不是继续增加规则，也不是简单删除 Harness 核心，而是：

> 减少规则文字，提高引导密度；让 Harness 在关键时刻重新指出当前重点、关键判断和最有信息增益的下一步。

## 二、对 0.11 的准确评价

0.11 的架构方向正确，应当保留：

- 常驻内核已经从 0.10 的大段治理规则缩短为用户结果、相关设计与事实、完成标准和最短证据；
- 九类 guidance 已按状态或显式 intent 触发，无关模型、心跳、恢复和 push 规则不再全部常驻；
- completionStandards、authorityDesign、facts、routeBasis、动态 capability、依赖并行、300000ms 心跳、reported/accepted 分离、evidenceRef、问题级失败恢复和安装回滚已经形成产品能力；
- Harness 仍只投影和记账，实际 agent 调用由指导模型使用宿主工具完成。

但 0.11 主要解决了“什么时候加载提示”，尚未完全解决“加载什么样的提示”。当前仍存在六个差距。

### 1. 事件片段仍是压缩后的规则书

`lib/guidance.js` 中多数 fragment 仍以条件枚举、禁止项、例外和治理术语为主体。它们比 0.10 短，也只在相关事件出现，但模型在该事件内仍被要求同时记住多种不应发生的情况。

下一版本必须把事件内容改为决策引导，而不是把同一套治理规则切成九段。

### 2. 多事件只做文本拼接，没有形成唯一当前重点

当前 `guidance.select()` 会把同时成立的 fragment 依次连接。active、reported、recovery 等状态并存时，模型收到多段同级规则，没有一个经过综合后的当前最高优先级。

下一版本必须把多个状态先综合成一个当前工作焦点；其他状态作为简短事实保留，不能继续把所有 fragment 原样叠加。

### 3. 同一语义仍在多个运行时表面重复

并行、心跳、accepted、evidenceRef、进展和失败升级等语义，同时出现在 event guidance、skills、Hook lifecycle 和任务数据中。各处单独看都有理由，但同时进入上下文时会重复强化治理语义。

下一版本必须落实“一个语义，一个运行时权威来源”。其他表面只引用结构化结果，不再重新讲一遍完整规则。

### 4. 用户结果可能比治理字段更早被压缩

当前单 work-unit Hook 摘要只内联有限数量的完成标准、设计和事实，并截短 goal；status、dispatchReady、routeBasis、scope、forbidden 和 provenance 等治理字段仍占固定位置。完整任务包虽然可以通过 status JSON 读取，但模型第一眼看到的上下文可能出现治理信息完整、用户结果被摘要的优先级倒置。

下一版本必须保证用户目标和全部必需完成标准优先完整可见。上下文不足时，应先删除重复治理说明，再使用明确标识为完整的安全 carrier；不得用 `…+N` 或普通截断让模型误以为已经看完成功条件。

### 5. skills 仍承担了过多规则复述

`skills/split-work.md` 和 `skills/root-cause.md` 同时包含方法、字段合同、反例分类、工具调用和升级规则。一旦 skill 与相同 event guidance 同时使用，同一语义会再次进入上下文。

下一版本中，skill 应成为短的决策方法或按需操作说明，不再复制状态机、失败账和事件 guidance 已经能够提供的内容。

### 6. 当前验收主要证明提示结构，没有证明模型行为

0.11 测试能够证明关键词存在或缺席、事件选择正确、字段没有丢失、无关状态不投影。这些测试很重要，但只能证明提示被正确送达，不能证明模型因此选择了最短路线、抓住了用户重点或避免了保守空转。

下一版本必须加入真实模型行为评测。结构测试继续保留，但不能再单独授予“引导能力 PASS”。

## 三、下一版本冻结的设计原则

### 1. Prompt 是方向盘，不是规章汇编

常驻和事件提示的主要内容应当持续强化：

1. 用户现在要得到的结果；
2. 会改变路线的相关设计和真实事实；
3. 当前唯一最重要的判断；
4. 最短、最高信息增益的下一动作；
5. 新证据出现后是否需要更新路线。

模型不需要在每个事件重新阅读整套治理理由。

### 2. 正向引导优先，硬边界精确出现

- 普通 guidance 优先说明应该看什么、判断什么、接下来做什么；
- 负面规则只保留高代价、不可逆或权限相关的真实硬边界；
- 硬边界必须绑定明确对象、范围和触发事件，只出现一次，不得类推为普遍禁令；
- 大量具体失败例子移到测试 fixture、评测场景和设计文档，不进入普通运行时上下文。

### 3. 一个语义只允许一个运行时权威来源

建议的所有权如下：

| 语义 | 唯一运行时来源 | 其他表面的责任 |
| --- | --- | --- |
| 用户目标与完成标准 | current leaf / work-unit package | Hook 只完整投影或指向完整 carrier |
| 相关权威设计与事实 | leaf/work-unit package | guidance 只提出当前需要核实的关键点 |
| 当前事件焦点 | guidance synthesizer | skills 不复述事件规则 |
| accepted、依赖、失败次数、租约 | delegation/state code | prompt 只显示当前事实和下一判断 |
| 模型 availability/capability | 当前真实工具面或结构化 manifest | 不保留静态历史目录 |
| 通用跨项目兜底 | 用户外部全局 AGENTS | Harness 不安装或改写，只报告实际上下文影响 |
| 项目或任务硬边界 | 项目规则或 current leaf | 只在相关任务/事件投影 |

### 4. 多事件必须合成为一个当前焦点

下一版本不能继续简单返回多段同级 prose fragments。无论同时存在多少状态，运行时 guidance 应形成一个最小决策包：

```json
{
  "focus": "当前最需要解决或判断的事情",
  "decisionQuestion": "模型现在必须回答的一个问题",
  "nextAction": "最短、可验证的下一动作",
  "stateFacts": ["只保留会改变当前动作的事实"],
  "hardBoundaries": ["仅当前事件真正命中的精确边界"]
}
```

字段名称属于推荐 HOW，可以在正式升级计划中调整；必须保持的 WHAT 是：模型一次只看到一个综合后的当前重点，而不是多段规则拼接。

### 5. 用户结果拥有最高上下文保真度

运行时上下文的保留顺序必须是：

1. 当前用户目标和全部必需完成标准；
2. 相关权威设计与会改变路线的真实事实；
3. 当前焦点、判断问题和下一动作；
4. 当前真正命中的硬边界；
5. operational metadata。

预算不足时，从第 5 项开始压缩。不能为了完整展示 status、scope、provenance 或治理术语而截断用户成功条件。

### 6. 保留能力，但尽量由状态机执行

以下能力不能因为提示减重而消失：动态选模、依赖并行、五分钟心跳、限制介入、reported/accepted 分离、evidenceRef、busy≠progress、有效失败去重、Terra/Sol 问题级恢复、旧系统事实边界、安装迁移、回滚和 push gate。

能由代码和账本确定的规则，应由代码给出当前状态和允许的下一转换；模型只需要看到当前决定，不需要反复阅读完整状态机说明。

## 四、九类事件内容的改造方向

保留 0.11 的事件名称和物理 Hook 边界，重做事件输出：

| 事件 | 下一版本主要引导 |
| --- | --- |
| `leaf-definition` | 用户最终需要什么结果；哪些设计和事实会改变成功含义 |
| `route-clarification` | 当前最关键的未证假设是什么；用哪一个最短证据验证 |
| `pre-dispatch` | 这个 unit 必须证明什么；需要给 writer 的最小完整信息是什么 |
| `agent-active` | 是否已有直接证据需要介入；没有则给出下一观察时间 |
| `agent-reported` | 实际结果证明了哪条完成标准；最短缺口是什么 |
| `problem-recovery` | 哪个实质决定刚被证据否定；当前应重选哪一层路线 |
| `leaf-closeout` | 用户要求的产品结果是否全部出现；哪些仍是未知或未证明 |
| `legacy-fact` | 当前旧载体能提供哪一条事实；它不能替代哪一项未来设计 |
| `push-attempt` | 当前精确目标和授权是否成立；代码 gate 直接给出允许或拒绝 |

这张表描述引导方向，不要求把问题逐字复制进运行时。正式实现应根据当前结构化状态生成最短表达。

## 五、必须新增的行为评测

### 1. 评测目标

不只检查模型说了什么，还要检查它接下来准备做什么。至少评估：

- 第一动作是否命中用户结果和最短证据；
- 是否在真实信息足够时直接推进；
- 是否因局部错误回滚、停止或否定无关成果；
- 是否把罕见且有明确范围的规则扩大成普遍禁令；
- 是否在测试全绿但功能缺失时仍判返修；
- 是否在默认路线被事实否定后主动换路，而不是继续加版本或补丁；
- 是否只在高信息价值问题上询问用户；
- 多事件并存时是否抓住唯一当前重点。

### 2. 基线对照

对同一组任务分别运行：

- 0.11 当前 guidance；
- 下一版本候选 guidance；
- 重复加入无关禁令或历史事故的压力上下文；
- 删除重复治理语义后的最小上下文。

比较路线选择、首个动作、用户提问、无效工作轮次和完成标准命中情况。不能只比较回答措辞。

### 3. 动态模型覆盖

评测模型必须来自执行时真实工具面，不建立静态目录。工程、前端和普通指导任务按当时真实能力选择相关模型；同一模型至少重复足以识别明显不稳定性的次数。正式计划再根据实际成本定义样本量和通过阈值，不制造虚假精确。

### 4. 结构测试仍然保留

继续验证：无关 guidance 物理缺席、intent allowlist、状态确定性、carrier 完整、旧输入只读、accepted 证据门、迁移回滚和 candidate 确定性。但结构 PASS 只能证明载体正确，不能替代模型行为 PASS。

## 六、下一版本的产品验收标准

下一次升级只有同时满足以下条件才可以接受：

1. 常驻内核仍然短，并主要强化用户结果、相关事实、最短路线和证据更新；
2. 同时成立的多个事件被合成为一个 focus/decision/next-action，而不是 prose 拼接；
3. 用户目标和全部必需完成标准不会被普通摘要静默截断；
4. 同一治理语义不再在 base、guidance、skills 和 Hook 中重复解释；
5. 普通运行时 guidance 不携带大段具体禁令和失败例子；
6. 精确硬边界仍能在相关事件生效，并且不扩散到无关任务；
7. 现有 0.11 动态模型、并行、心跳、accepted、失败恢复、安装与回滚能力全部回归通过；
8. 真实模型行为评测证明候选比 0.11 更稳定地选择最短有效路线，并减少治理正确但实际无效的工作；
9. 独立 reviewer 必须查看真实模型行为记录和实际调用路径，不能只复核 prompt 文本或测试数量。

## 七、非目标

- 不是删除权限、安全或不可逆操作边界；
- 不是让模型忽略 current leaf、完成标准或证据；
- 不是新增第二套 prompt 数据库、事件总线、provider adapter、daemon 或 agent 调度器；
- 不是把哲学原则和大量方法论重新写进常驻内核；
- 不是为所有情况加入更多例子；
- 不是要求模型先理解整个项目；
- 不是让每个决定都重新询问用户；
- 不授权 Harness 修改用户全局 `AGENTS.md`。全局兜底是否更新仍是独立的用户环境变更。

## 八、建议的下一次计划拆分

正式升级计划可以从以下工作面展开，但必须在用户明确启动后另行建立 stage/leaf：

1. `PG00`：捕获 0.11 实际上下文组合和真实模型行为基线，冻结直接反例；
2. `PG01`：实现多事件 guidance synthesizer 和唯一当前焦点；
3. `PG02`：重排 Hook 上下文优先级，保证用户结果与完整完成标准不被静默截断；
4. `PG03`：清理 base/guidance/skills/Hook 的重复语义，建立单一运行时所有权；
5. `PG04`：建立真实模型行为 A/B 评测和重复语义压力测试；
6. `PG05`：集成、迁移、candidate、主管验收与未参与实现的独立产品复核。

PG01 与 PG02 只有在实际写面分离时才并行；PG03 在两者接口稳定后统一收口；PG04 可以先准备 fixture，但最终评测必须使用集成后的真实候选。
